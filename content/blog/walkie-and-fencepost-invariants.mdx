Prompts can ask a model to stay cautious, and confirmation dialogs can ask a user to double-check. Neither holds up well under fatigue or asynchronous work. In two recent projects, I tried to move critical safety boundaries out of UI copy and into hardware inputs or query rules: [Walkie](/projects/walkie), a personal project on an M5StickS3 watch, and **Fencepost**, a DECO7285 course project built with teammates where neighbours share possum sighting videos.

On Walkie, AI coding tools (Claude Code) wrote most of the code; I set the rules, reviewed the output and verified it on the watch. On Fencepost, AI coding tools helped with my part: across the repository's branches, 69 of my 271 commits carry a Claude co-author line (counted on 25 November 2026).

## Walkie: physical keys as the permission boundary

Walkie is meant to let me answer Claude Code from my wrist during long tasks. Voice is tempting right up until the agent asks to run a destructive shell command or write outside its workspace; approving that by voice alone fails easily with a noisy room or a mis-transcription.

So the **physical keys** on the M5StickS3 carry the decision:

- **Explicit pairing**: a new key is offered to the watch, and the desktop adopts it as `pair.key` only after the front key is pressed. The side key, or 30 seconds without an answer, refuses it.
- **Discrete approval**: a tool permission prompt pauses the Node 24 bridge until a key is pressed. A short front press allows; a short side press denies; holding the front key denies and records a spoken reason.
- **Dual-boot guard**: Walkie shares the watch with [On The Beat](/projects/onthebeat), so `firmware/guard.py` refuses the `erase`, `uploadfs` and `uploadfsota` build targets by name, because they would write outside Walkie's own partition.
- **Blind relay**: off the cable, frames are sealed with AES-256-GCM under a key derived from `pair.key`, so the Fly.io relay forwards ciphertext and cannot read prompts or tool names.

**What has run where:** gate H, the check of the screens and keys, passed on the real watch, and a whole turn ran over USB with synthetic speech fed into the watch microphone. Gate L ran a stand-in device through a real relay, not the watch. Gate P5 (pairing and the sealed link on the watch) was written, and I have no record of it being run. Gates M and N, the watch working away from the cable, have no run record either. Only I have used Walkie.

## Fencepost: revoking access cuts the model off too

Sharing backyard sightings can expose a home and a household's evening routine. Hiding a shared item in the interface is not enough if its text lingers in an AI assistant's retrieval context.

In Fencepost, two rules live in the data boundary itself:

1. **No location metadata stored**: video frames are re-encoded in the browser, which drops metadata, and the server drops any still that arrives carrying an EXIF or XMP block. The schema has no location field.
2. **Grants checked before context**: the assistant's context is built from a separate query that checks active sharing grants. The data-layer tests check that once a resident revokes a share, the next assistant call no longer reads the hidden sighting. <AnchorNote term="query-layer invariant" label="Architecture note" note="Separating timeline queries from assistant context queries means UI caching does not carry revoked data back into an LLM prompt." />

The public demo leaves handle login lightweight so reviewers can try the flows, while grant checks stay in the data layer.

| Trust failure surface | Soft UI warning | Structural rule (Walkie / Fencepost) |
| --- | --- | --- |
| Destructive shell prompt | Voice confirmation (`"Yes"`) or a modal | The bridge waits for a front or side key press on the watch |
| Shared firmware flashing | A README warning before flashing | `firmware/guard.py` refuses the `erase` and `uploadfs` targets |
| Cloud relay privacy | TLS only, with the relay reading plaintext | AES-256-GCM envelope keyed from `pair.key` |
| Revoked AI retrieval | Item hidden in the UI while prompt context stays stale | Active grants checked before the assistant's context is built |

## Shared lesson

Good interaction design for autonomous tools does not stop at polite microcopy. Putting the rule where skipping it is structurally hard makes the interface above it calmer to use. Try Walkie's key flow in the [Interaction Lab](/lab) or question these decisions in the [AI Lab](/ai).

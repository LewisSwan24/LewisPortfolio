Autonomous coding workflows rarely fail cleanly when optimism is built into their queues. A tool call times out, a bridge drops half a packet, or a cloud relay returns an ambiguous error, and a fail-open interface quietly retries or falls back to a default permission.

## Four fail-closed rules across hardware and web

Across [Walkie](/projects/walkie), [Resume Autofill](/projects/autofill) and this site's [AI Lab](/ai), the approval paths follow four fail-closed rules. Walkie and Resume Autofill are personal projects whose code was mostly written by AI coding tools (Claude Code); I set the rules, reviewed the output and verified it.

1. **No answer, no trust**: Walkie writes a new pairing key as a candidate, `pair.key.new`, before the watch answers. Only after a front-key press within 30 seconds is it renamed over `pair.key`; a refusal or a timeout leaves the working key untouched, and the unanswered candidate is offered again next time.
2. **Classify the disconnect before retrying**: Walkie's offline screen says which link is down (no Wi-Fi, no relay, or PC offline) instead of showing a vague spinner.
3. **The final submit stays human**: Autofill can press "Next" on multi-page forms but never presses the final Submit.
4. **No evidence, no answer**: in the [AI Lab](/ai), if retrieval finds no matching record in the site's evidence corpus, the workbench declines rather than writing prose to fill the gap.

## Stepping through failure transitions

The [Protocol Replay Studio](/studio/replay) steps through simulated fault frames, such as a USB cable change mid-turn. The frames are hand-authored to explain the rules, not captured from the device. Each case's [Red-Team defense](/ai) lists the challenges these rules have to answer.

Many AI interfaces optimize for one goal: making every action look effortless. Prompts auto-complete, destructive confirmations highlight a glowing primary button, and job-application tools guess answers the user never checked. My argument, which is a design position rather than a measured result, is that when everything looks smooth, oversight shrinks into muscle memory.

Three of my personal projects, [Lamplight Nook](/projects/lamplight), [Resume Autofill](/projects/autofill) and [Walkie](/projects/walkie), build refusal and uneven friction into the interaction. AI coding tools (Claude Code) wrote most of their code; I set the rules, reviewed the output and verified it. So far only I have used them.

## Why "100% auto-fill" is a false kindness

Applying to dozens of graduate positions means retyping the same work history again and again. An autofiller that wants to impress is tempted to fill every visible field, including visa eligibility, salary expectations or custom essay answers.

In [Resume Autofill](/projects/autofill), that temptation carries uneven risk: the extension gets credit for convenience, while the applicant carries the consequence if a wrong compliance answer goes through. So instead of one magic button, every field lands in one of three visible outcomes:

1. Matched fields fill (2px solid outline).
2. Uncertain matches, or dropdowns with no matching option, wait for the person (2px dashed outline).
3. Fields the tool cannot map, or where filling failed, are left for the person (3px solid outline).

Consent boxes, declarations, passwords and verification codes are never filled, and the extension never presses Submit.

**Measured scope:** the repo has six synthetic fixture pages and a six-shot light/dark screenshot suite of the extension's own UI. The screenshots check how the button, side panel and options page look, not how accurately fields are mapped. How the mapping holds up as job sites change has not been sampled.

## Blocking habitual Enter-key fatigue

A similar failure appears when supervising long-running coding agents. Logs stream faster than a person can check them, and many desktop dialogs put default focus on **Continue**, so pressing `Return` keeps work moving.

In [Lamplight Nook](/projects/lamplight), an agent task is staged as a café crew with a blackboard plan. Risky cards put initial focus on **Not now**, and Enter or Esc on such a card means "Not now", so dismissing it refuses rather than proceeds. When it works in a folder you lend it, it keeps the originals so changes can be undone.

On [Walkie](/projects/walkie), the keys create the same asymmetry: speech can describe an intent, but a tool permission waits for a deliberate press of the front key (allow) or side key (deny) on the M5StickS3. The keys were checked on the watch itself; using Walkie away from the cable has no on-device run record yet.

| Pattern | Convenience-first default | Default used here |
| --- | --- | --- |
| Uncertain application field (`Autofill`) | A model fills its best guess silently | Dashed or thick outline, with the field left for the person |
| Final job submission (`Autofill`) | Auto-advances through Submit | Presses Next only; Submit stays with the person |
| Risky desktop card (`Lamplight Nook`) | Enter triggers Proceed | Focus starts on **Not now**; originals kept in lent folders |
| Tool approval (`Walkie`) | A spoken "Yes" runs the command | A front or side key press on the watch is required |

## Intentionally un-automated

Good AI interaction design says clearly what the machine **will not guess or trigger on its own**, and puts a calm pause right before irreversible steps, even at the cost of one more click. Try all three in the [Interaction Lab](/lab) or question them in the [Rationale AI Lab](/ai).

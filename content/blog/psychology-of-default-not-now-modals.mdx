Anyone working with an IDE, a browser and a background coding agent at once will see focus jump. My working assumption, which I have not measured, is that people dismiss modal interruptions faster than they read them. If a confirmation dialog puts keyboard focus on `Approve`, one unintended keystroke can commit an irreversible file write or shell command. I call that **Enter-key fatigue**.

## Designing against muscle-memory rubber-stamping

[Lamplight Nook](/projects/lamplight) is a personal project whose code was mostly written by AI coding tools (Claude Code); I set the rules, reviewed the output and verified it, and so far only I have used it. Its risk confirmation cards follow three rules:

1. **Default focus stays on `'Not now'`**: pressing `Enter` or `Esc` out of reflex means "Not now", so the risky action does not run. Approving takes a deliberate move to the other button.
2. **Limits behind the card**: each run has a spending cap, and when the agent works in a folder you lend it, the originals are kept so changes can be undone.
3. **Plain naming over dark patterns**: `'Not now'` is neutral. It does not shame the person (`"No, keep my workflow slow"`) for choosing to wait.

## Physical parallels beyond desktop modals

The same idea shapes [Walkie](/projects/walkie), where approve and deny sit on different faces of the watch, the front key and the side key, so one thumb movement cannot easily be mistaken for the other.

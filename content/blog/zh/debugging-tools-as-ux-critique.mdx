很多团队把调试工具当成上线前就该删掉的临时脚手架。我在桌面 AI 代理、两个硬件项目和这个网站上做下来，发现可检查的工具用处更大。评审可以借这类工具，看到静态画板和顺利演示里跳过的少见状态。

## 可检查的工具在哪里派上用场

1. **[Lamplight Nook](/zh/projects/lamplight) 的录制事件回放。** 只靠真实 Claude SDK 现跑，超预算和卡住这类少见状态很难随时复现。Lamplight Nook 有一个调试面板，可以回放匿名化的真实事件录音，这些画面就能并排拿来评审。Lamplight 的代码大部分由 Claude Code 写成，规则由我来定，输出由我审查，我自己也在用。
2. **Walkie 与 MazeRunners 的协议帧单步。** [协议帧重放台](/zh/studio/replay) 可以逐帧查看两件事。一是 Walkie 一轮对话进行中插上 USB 线，这一轮会作废。二是 MazeRunners 的三次取样去抖和 400 ms 冷却，怎样让球经过一次只记一次。这些帧是按逻辑手写的模拟数据，并非硬件实录，只能用来解释规则，不能当证据。
3. **[实验室状态机](/zh/lab#fsm-explorer) 的可达性检查。** 白板上画的状态迁移图，看上去闭环了，未必真的闭环。这个工具用广度优先遍历，标出所有回不到待机态的状态。这个工具是作为评审辅助做的，目前还没有记录显示，这项检查在我的项目里抓到过真实缺陷。

## 可检查性本身就是一种设计诚实

作品集把重放台和 [红队对抗答辩](/zh/ai) 一并交给评审，对方就不必只凭一张好看的截图去相信。评审可以自己把指针拖到边界状态上看。前提是要告诉对方，哪些数据是模拟的。

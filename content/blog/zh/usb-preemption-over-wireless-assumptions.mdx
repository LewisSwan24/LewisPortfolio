主打无线的设备演示，总爱承诺在书桌和沙发之间无缝切换。我担心的是，把一轮语音拆在 USB 串口和 WebSocket 中继两条链路上拼起来，正好会制造半截指令和重复的工具调用。

## 抢占，但不静默拼接

在 [Walkie](/zh/projects/walkie) 里，桥接遵循两条规则，写在项目 README 里。Walkie 的代码大部分由 Claude Code 写成，规则由我来定，输出由我审查，下面标明「已验证」的部分由我验证。

1. **数据线优先**：桥接先在 USB 上找手表，只有没插线、并且已经设好配对密钥和中继地址时，才走中继。走中继期间，每 3 秒找一次数据线，一插上就切过去。经数据线传输时，音频默认是 `16 kHz` PCM。
2. **一切换就放弃这一轮**：数据线和中继之间的切换并不无缝。正在进行的一轮会像断线时一样被丢弃，不会把一条链路上的半轮拼到另一条上。

**已经检查过什么：** 经 USB 的整轮对话已经在真表上跑通。gate M 负责在表上检查中继与数据线互相切换，目前还没有跑。所以第二条规则只是设计好并写进了文档，还没有在真表上验证。[协议帧重放台](/zh/studio/replay?track=walkie) 里是一段手写的模拟数据，可以单步查看。

## 坦然中断，胜过脆弱的连续

这是我的推理，没有测量数据。一轮话重说一遍只要几秒；一段拼接的录音如果变成半截 Shell 命令送到代理那里，善后成本会高得多。丢弃这一轮，是代价更小的失败。

One tempting shortcut in AI prototypes is to load a whole user table into context, append `"Do not mention private or deleted items"` to the system prompt, and call it private. My view is that this cannot hold: once someone revokes a shared link or asks a clever follow-up, nothing stops the model from quoting the entry it still has.

## Query isolation before the model sees a token

In **Fencepost**, a DECO7285 course project I built with teammates where neighbours share possum sighting videos, and in the retrieval pipeline behind this site's [AI Lab](/ai), revocation lives below the prompt layer:

1. **Separate timeline and assistant queries**: the timeline query and the assistant's context query do not share a cache. Share tokens are stored hashed, and the data-layer tests check that once a share is revoked, the next assistant call no longer reads that record.
2. **No location to leak**: video frames are re-encoded in the browser, which drops metadata, and the server drops any still that arrives carrying an EXIF or XMP block. Media records keep only a storage key, and the schema has no location column for an assistant summary to draw on.
3. **ID-only reranking**: in the [AI Lab](/ai), even when an optional model reranks candidates, it may return corpus IDs only. The text shown comes from the site's static evidence tables, so the model cannot add claims of its own.

## The same principle in local-first tools

The same refuse-at-the-data-boundary idea appears in two personal projects whose code was mostly written by Claude Code, with me setting the rules, reviewing and verifying: in [Resume Autofill](/projects/autofill), a unit test fails if the Android keyboard code uses any networking class, and in [Walkie](/projects/walkie), the Fly.io relay only ever handles AES-256-GCM ciphertext.
